# 如何回溯到能运行的代码

最稳妥的方法是新建一个恢复目录。这样不会影响当前正在修改的文件，也不用执行 reset --hard 或 clean。

## 恢复基本无线图传 V1.0

```powershell
git clone --branch v1.0 https://github.com/ukg44059-lang/mini_cam.git mini_cam_restore_v1.0
cd mini_cam_restore_v1.0
python tools/verify_snapshot.py V1.0
```

标签检出后处于 detached HEAD，查看和编译都可用。要继续修改，先创建分支：

```powershell
git switch -c fix/from-v1.0
```

代码在 V1.0/ 中。构建命令、接线、串口和固件文件见该目录 README.md。恢复仓库文件不会自动恢复板子里的固件；需要分别使用同一版本的 STM32、CC1310 TX、CC1310 RX 固件。硬件接线、串口编号和工具链也是恢复条件的一部分。

## 恢复 V1.1 测试工程

```powershell
git clone --branch v1.1-test https://github.com/ukg44059-lang/mini_cam.git mini_cam_restore_v1.1-test
cd mini_cam_restore_v1.1-test
python tools/verify_snapshot.py 'V1.1(test)'
```

这是测试代码保存点，尚未完成8项真实硬件验证。不能把恢复该标签等同于恢复“已验证可用”的测试系统。需要恢复已经验证的基本图传时，选择 v1.0。

## 已有仓库时查看历史

```powershell
git fetch origin --tags
git log --oneline --decorate --all
git tag -n
git show v1.0:README.md
```

README 和 CHANGELOG.md 说明各次更新；GitHub 提交页提供该更新的完整 SHA。标签是方便选择的名称，提交 SHA 是不可歧义的内容标识。恢复关键实验时，额外记录完整提交 SHA 和固件 SHA-256。

## 后续更新的约定

1. 改动之前先提交当前可用状态；较大修改在新分支上做。
2. 每次有意义的更新都提交，并在 CHANGELOG.md 写当地日期、修改了什么、验证到哪一步和已知问题。只有修改日期、没有提交或推送，不能形成可恢复的远端备份。
3. 验证后再建立新标签并推送，例如 `v1.1-test.1`、`v1.1`；已有标签保持不动，不复用同一个名称覆盖旧代码。
4. 更新对应版本的固件、构建记录、测试结果和 SNAPSHOT.json；文档中保留旧版本已知问题。main 可以继续前进，已发布标签保持原样。
5. 定期 `git push origin main --follow-tags`，确认 GitHub 能看到提交和标签。仅本地 commit 不能防止本机磁盘故障。

当前仓库保留原始源码副本，不会追溯生成它们在首次导入之前不存在的 Git 提交历史。
